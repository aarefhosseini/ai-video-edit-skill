# Real screen footage

Map every requested visual to the exact real page/action and the claim it supports before recording. Determine authorized access and whether the state is public, test, demo, or live. Use host-supported browser tools under their actual documentation. A local source-code feature alone doesn't prove the live UI or payment path works.

Record readable, steady footage: known viewport/device, content fully loaded, intentional pointer position, continuous smooth scroll, enough lead-in/out, and time to understand the selected detail. Let visible animations finish. Capture a mobile flow when relevant to the story. Avoid unnecessary tours and repeated scroll resets.

Use existing authorized test state. Recording doesn't authorize transactions, changing settings/data, issuing credit, registering orders, sending messages, or accepting terms. If a desired shot requires those actions, first identify an existing state or ask for the missing authorization/material. Do not retry an ambiguous mutation.

If a real continuous recording is unavailable, a genuine screenshot with animated crop may demonstrate static content. Label that production choice and don't present it as interaction evidence. A generated or rebuilt interface is an illustration, not a recording of the actual app.

Preserve demo/sample indicators when necessary to understand the claim. Remove sensitive material from the exported clips, then review frames throughout the full interval: mobile numbers, identification numbers, OTP, account details, notifications, other customers, and session tokens. Package only sanitized exports; never copy browser profile/session data into a deliverable.

For every capture record source URL/context, date, device/viewport, relevant action, clip in/out, demo/live status, and the supporting claim. If an asset becomes inaccessible, keep already-authorized usable footage and clearly list missing essential shots.
